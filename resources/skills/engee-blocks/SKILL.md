# Engee Blocks

Когда skill активирован:

1. Считай эту папку локальным индексом по библиотеке блоков Engee.
2. Для быстрого поиска блоков сначала используй `blocks.json`.
3. Для чтения описания блока предпочитай `doc/md`, а `doc/html` используй, когда нужна исходная HTML-разметка.
4. Для построения моделей со всеми блоками библиотек используй `all_blocks/add_blocks/*.jl`.
5. Для просмотра уже собранных моделей используй `all_blocks/models/*.engee`.
6. Если нужны реальные `blockValues`, `blockInputs` и `blockOutputs`, бери их из `.engee`-моделей, а не только из документации.

## Что есть в skill

В папке skill лежат:

- `blocks.json` — структурированный индекс блоков
- `doc/html/` — локальные HTML-страницы документации
- `doc/md/` — те же страницы в Markdown
- `all_blocks/add_blocks/` — Julia-скрипты для сборки моделей по библиотекам
- `all_blocks/models/` — готовые `.engee` модели, собранные из этих скриптов
- `all_blocks/models/blocks_enrichment_summary.json` — сводка обогащения `blocks.json` данными из моделей
- `enrich_blocks_from_models.py` — скрипт, который извлекает данные блоков из `.engee` и обновляет `blocks.json`

## Что содержит `blocks.json`

`blocks.json` — это основной индекс блоков. В нём сейчас `1264` записей.

Каждая запись содержит:

- `blockNameEN` — английское имя блока
- `blockType` — программное имя блока
- `path` — полный путь блока в библиотеке Engee, например `/5G/5G Waveform Generator`
- `blockSet` — верхнеуровневый раздел библиотеки
- `url` — URL страницы блока в онлайн-документации Engee
- `blockValues` — словарь значений и параметров блока, извлечённый из модели
- `blockInputs` — список входных портов блока без поля `portID`
- `blockOutputs` — список выходных портов блока без поля `portID`

Используй `blocks.json`, когда нужно:

- найти блок по имени
- найти все блоки конкретного раздела
- получить `blockType`
- получить путь для `engee.add_block(...)`
- связать локальный markdown/html с исходным URL документации

Важно:

- `blocks.json` индексирует именно блоковые страницы
- обзорные, tutorial и article-страницы в него обычно не входят
- если блока нет в `blocks.json`, это не обязательно ошибка: страница могла быть обзорной, а не страницей отдельного блока
- поля `blockValues`, `blockInputs`, `blockOutputs` получены не из документации, а из реальных `.engee`-моделей
- для `blockInputs` и `blockOutputs` поле `portID` намеренно удаляется как нестабильный технический идентификатор
- при сопоставлении данных модели с `blocks.json` нельзя полагаться только на `blockType`, потому что один `blockType` может повторяться у разных блоков и служебных узлов
- надёжное сопоставление идёт по паре `(blockSet, path)`

## Что можно найти в `doc/html/`

`doc/html/` содержит локально сохранённые HTML-страницы документации Engee. Сейчас там `1561` файла.

Это исходная разметка страниц, полезная когда нужно:

- сохранить или проанализировать HTML-структуру статьи
- извлечь данные из таблиц, параметров, портов и секций
- найти исходные ссылки, изображения и якоря
- восстановить точную структуру документа

Типично в HTML-странице блока можно найти:

- заголовок блока
- `blockType`
- `Path in the library`
- описание блока
- разделы `Ports`
- разделы `Parameters`
- таблицы типов, значений по умолчанию и имён параметров для программного доступа
- ссылки на примеры и связанные материалы

Нюанс:

- в `doc/html` иногда могут встречаться артефакты кодировки из исходного сайта
- если нужна более удобная для чтения версия, сначала смотри `doc/md`

## Что можно найти в `doc/md/`

`doc/md/` содержит те же страницы документации, но в Markdown. Сейчас там тоже `1561` файла.

Это основной формат для чтения содержимого человеком и для работы агента с текстом. Он удобен, когда нужно:

- быстро прочитать описание блока
- извлечь `blockType`, путь и параметры без разбора HTML
- искать по тексту через `rg`
- использовать документацию как текстовую reference-базу

Типично в Markdown-странице блока можно найти:

- краткое назначение блока
- `blockType`
- путь в библиотеке
- подробное описание
- входные и выходные порты
- параметры, их значения по умолчанию и программные имена
- ограничения по типам данных
- примеры и связанные ссылки

Рекомендуемый порядок:

1. Ищи блок в `blocks.json`
2. Читай содержимое блока в `doc/md`
3. Если нужна точная разметка или особые детали страницы, переходи в `doc/html`

## Зачем нужны `all_blocks/add_blocks/*.jl`

В `all_blocks/add_blocks/` лежат `16` Julia-скриптов, по одному на каждый верхнеуровневый раздел библиотеки.

Каждый такой файл:

- создаёт модель Engee для конкретной библиотеки
- добавляет в неё все индексированные блоки этого раздела
- выполняет `engee.arrange_system(engee.gcs())`
- сохраняет результат в `.engee`
- закрывает модель

Типовой сценарий внутри `.jl`:

- `engee.create(...)`
- список блоков
- цикл `engee.add_block(...)`
- `engee.arrange_system(engee.gcs())`
- `engee.save(...)`
- `engee.close()`

Эти файлы нужны, когда требуется:

- автоматически собрать тестовую модель со всеми блоками раздела
- проверить, что блоки из раздела реально создаются
- получить готовую модель-каталог по библиотеке
- воспроизвести сборку модели в Engee API или вручную

## Что содержится в `all_blocks/models/*.engee`

В `all_blocks/models/` лежат готовые результаты выполнения этих `.jl`-скриптов. Сейчас там `16` файлов `.engee`.

Каждый `.engee`:

- это сохранённая модель Engee
- обычно соответствует одному верхнеуровневому разделу библиотеки
- содержит блоки, добавленные из соответствующего `.jl`-скрипта
- по сути является zip-архивом с несколькими JSON-файлами

### Как устроен `.engee`

Практически полезно считать `.engee` zip-архивом. Внутри обычно есть:

- `root.json`
- множество дополнительных JSON-файлов, часто названных UUID
- служебные файлы вроде `storage.json`, `model.json`, `logs.json`, `configset.json`, `callbacks.json`

Если задача состоит в извлечении данных по блокам, используй:

- `root.json`
- все остальные JSON, кроме `storage`, `model`, `logs`, `configset`, `callbacks`

Внутри этих JSON полезные данные обычно лежат в `state`. Для блоков особенно важны:

- `blockPath`
- `blockType`
- `blockName`
- `blockValues`
- `blockInputs`
- `blockOutputs`

Нюансы:

- `blockInputs` и `blockOutputs` содержат `portID`, но для долгоживущего индекса его лучше отбрасывать
- в моделях встречаются повторяющиеся payload-ы и служебные блоки
- один и тот же `blockType` может встречаться много раз, например у `SubSystem`, `Inport`, `Outport` и других типовых сущностей
- из-за этого извлечение в `blocks.json` надо привязывать к `(blockSet, path)`, а не просто к `blockType`

### Текущее состояние обогащения по моделям

`blocks.json` уже обогащён данными из моделей через `enrich_blocks_from_models.py`.

Последний зафиксированный результат:

- всего записей в `blocks.json`: `1264`
- сопоставлено с моделями: `1262`
- не сопоставлено: `2`
- дубликатов payload-ов при проходе моделей: `29`

Сводка лежит в `all_blocks/models/blocks_enrichment_summary.json`.

На данный момент не сопоставлены только:

- `Physical Modeling /Fundamental/Electrical/Sources/DC Current Source`
- `Physical Modeling /Fundamental/Electrical/Sources/DC Voltage Source`

## Практические знания по важным блокам

Ниже зафиксированы не только поля из документации, но и практические выводы, подтверждённые на реальных сборках и запусках моделей.

### `Programmable Voltage Source (Three-Phase)`

Для этого блока важно помнить про смешанные домены портов:

- порт `port` — это `AcausalElectricPowerSystems.ThreePhasePort`
- порт `n` — это `AcausalFoundation.Electrical.Pin`

Практический вывод:

- трёхфазный `port` подключай к машине или трёхфазной сети
- `n` подключай к `Electrical Reference`
- `Solver Configuration` подключай к той же фундаментальной электрической ветви, а не к `Grounded Neutral (Three-Phase)`

Если попытаться соединить `Solver Configuration` с `Grounded Neutral (Three-Phase)`, Engee даёт ошибку несовместимости доменов.

### `Grounded Neutral (Three-Phase)` и `Electrical Reference`

Эти блоки не взаимозаменяемы:

- `Grounded Neutral (Three-Phase)` работает на стороне трёхфазного power systems domain
- `Electrical Reference` работает в фундаментальном электрическом домене

В смешанных электрических схемах часто нужны оба блока одновременно.

### `Solver Configuration`

Для каждой связной acausal physical subsystem нужен ровно один `Solver Configuration`.

Практический симптом отсутствия или некорректного включения:

- `There must be one and only one Solver Configuration in subsystem`

### `Induction Machine Measurement`

Это один из самых полезных блоков для задач управления асинхронной машиной.

Практически подтверждено:

- вход блока подключается к `measurements_pu_out` машины
- параметр выбора канала называется `output`
- полезные варианты `output`:
  - `Rotor velocity`
  - `Stator d-axis current`
  - `Stator q-axis current`
- выходные значения отдаются в per-unit

Для FOC и похожих задач этот блок обычно проще и стабильнее, чем сборка отдельных физических датчиков вручную.

### Замкнутые контуры и алгебраические петли

При сборке контроллеров вокруг physical modeling блоков важно помнить:

- открытый контур физической части может успешно запускаться, а замкнутый контур уже нет
- ошибка `Обнаружена петля` обычно означает алгебраическую петлю
- для разрыва прямой зависимости полезны `Memory` и `Unit Delay`

Эти знания не внесены в `blocks.json`, потому что это не стабильные паспортные свойства отдельного блока, а практические runtime-заметки по их совместному использованию.

Используй эти файлы, когда нужно:

- открыть уже собранную модель, не выполняя скрипт повторно
- проверить визуальную компоновку блоков после `arrange_system`
- сравнить модели между разделами
- использовать их как артефакты пакетной сборки

## Как лучше работать с этим skill

Если пользователь спрашивает о конкретном блоке:

1. Найди его в `blocks.json`
2. Возьми `path`, `blockType`, `blockSet`, `url`
3. Открой соответствующий файл в `doc/md`
4. Если нужны реальные значения параметров и портов, смотри `blockValues`, `blockInputs`, `blockOutputs` в `blocks.json`
5. При необходимости проверь `doc/html`

Если пользователь спрашивает о целой библиотеке:

1. Отфильтруй `blocks.json` по `blockSet`
2. Используй `all_blocks/add_blocks/<Library>.jl`, если нужно собрать модель
3. Используй `all_blocks/models/<Library>.engee`, если готовая модель уже есть
4. Если нужны данные из внутреннего устройства модели, открывай `.engee` как zip и проходи JSON по правилам выше

Если пользователь хочет код добавления блока в модель:

- путь блока бери из `blocks.json -> path`
- человекочитаемое имя блока бери из `blockNameEN`
- верхний раздел бери из `blockSet`
- для примеров массовой сборки ориентируйся на `all_blocks/add_blocks/*.jl`

Если пользователь хочет массово извлечь параметры и порты блоков из моделей:

1. Используй `all_blocks/models/*.engee` как источник истины по фактическим payload-ам
2. Игнорируй `storage`, `model`, `logs`, `configset`, `callbacks`
3. Собирай `blockValues`, `blockInputs`, `blockOutputs`
4. Удаляй `portID` из портов
5. Сопоставляй результат с `blocks.json` по `(blockSet, path)`

## Практическая заметка

Этот skill описывает локальную копию библиотеки блоков Engee и её артефакты в проекте. Для выполнения `.jl` в реальном Engee-инстансе лучше сочетать его с:

- `engee-model-development` — когда нужно писать или менять Engee-код
- `engee-api` — когда нужно загрузить код в аккаунт Engee, выполнить его и скачать `.engee`

## Что помнить

- `engee-blocks` отвечает за знание локальной библиотеки блоков: поиск блока, `path`, `blockType`, параметры, порты, локальные HTML/Markdown-описания и артефакты `.engee`.
- `engee-api` отвечает за выполнение: старт/стоп Engee, выбор версии и timeout, запуск кода, загрузку файлов, `jobs/create` и скачивание артефактов.
- Практический рабочий сценарий часто такой: сначала `engee-blocks` помогает понять, что именно нужно собрать, затем `engee-api` помогает выполнить это в реальном инстансе Engee.
